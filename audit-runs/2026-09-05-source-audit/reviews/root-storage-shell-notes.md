# Root source review — storage, recovery, shell, and cross-flow validation

## Storage trace

Complete reads: all shared storage implementation/tests, all app storage production actuals, iOS safety tests, HomeRecoveryAvailability, LocalResumeRouter, App/AppNavigation/AppNavigationHost/AppBackPolicy, lifecycle policy, and app DI. Exact ranges/hashes are recorded separately.

- DI binds a single `FileBackedSnapshotStore` with strict Json and each platform filesystem. One store mutex serializes save/load/delete/list; JSON work uses Default, platform I/O has its own dispatcher. Errors exposed to UI are bounded fixed categories, not exception messages/private paths. Cancellation and fatal Errors are not converted into ordinary data failures.
- Snapshot filenames forbid separators, NUL, temporary names and excessive length. Mobile protected plaintext limit is 8 MiB; iOS reader caps allocation at limit+1, Android/Desktop stat before whole-file read. Filename is authenticated as AAD/MAC input. This does not establish TOCTOU robustness against an already-privileged writer to the sandbox. No external import path was found in these storage classes.
- Android: independent AES-256-GCM Keystore aliases for snapshots and credentials, fresh platform-generated nonce, tag validation, noBackupFilesDir, fsync before atomic rename with explicit non-atomic fallback. Key operations are behind singleton store mutexes. Bounds 16 KiB on secure values; plaintext mobile snapshots not silently used as fallback after encrypted authentication failure.
- iOS: independent 64-byte random snapshot key split for AES-CBC and HMAC; encrypt-then-MAC includes format header, filename, IV, ciphertext; verifies MAC before decrypt; constant-time fixed-sized comparison; key buffers cleared. Keychain create races reread durable winner. Files use complete Data Protection and backup exclusions; credential keychain items use AfterFirstUnlockThisDeviceOnly and no synchronization. Bounds/empty-data bridging are explicit. Native runtime/durability/locking guarantees not inferred from this read.
- Legacy handling: JSON-looking pre-encryption records get one-way protected replacement before legacy removal. Authenticated current-game envelope/state validation remains game-owned. iOS removes matching legacy plaintext in a finally block even if protected read fails; Android uses success-only `.also`. The latter difference is noted for further consequence analysis, not declared a defect merely from asymmetry.
- Desktop is an explicitly nonshipping development target: AES-GCM key in owner-only file on POSIX, sibling lock for first creation, no OS credential vault; rejoin credentials intentionally in memory. Reads of actual user settings/saves were not performed. Same-user key access is an intended limitation, not alleged mobile privacy leakage.
- `SerializedSnapshotWriter` serializes writes/discard, suppresses equal already-successful states, permits explicit rematch after a terminal-state deletion, and makes successful discard irreversible for that writer. Cancelled operations restore previous observable status. Tests exercise in-flight discard/flush and failure retries, but do not establish every caller's scheduling behavior; flow callers remain under review.
- Settings: validated English/Arabic and system/light/dark tags. Serialized backing writes precede flow publication. Android uses synchronous commit on IO; Desktop uses Preferences.flush on IO; iOS reports acceptance via NSUserDefaults, not guaranteed immediate durability. Platform initial preference reads may still block briefly; no measured freeze is claimed. Test fakes cannot prove mobile durability.

## Recovery and navigation trace

- Home probes local and multiplayer sources concurrently; local metadata scan offers at most eight entries plus an additional-record flag. File listing/migration itself may inspect more records, so the whole persistence operation is not proven constant-cost. Metadata parsing uses a JSON element tree rather than game decoding (the payload text still materializes).
- Session filename and authenticated envelope ID are compared before a resume route is offered/activated. Unknown/unreadable game IDs retain a Retry/Discard path. One record's ordinary error does not hide healthy records. No silent deletion of unreadable saves in the router.
- LocalResumeCoordinator has generation and origin-route guards plus identity-aware finalization; old cancelled work cannot navigate after a newer request/leave. It trusts SnapshotStore's Result contract rather than swallowing arbitrary implementation exceptions.
- AppNavigator owns one Home/Game/Recovery stack and one Settings stack, typed NavKey keys, monotonic game-entry IDs, process-local launch objects; no private launch/player data serialized into route keys. Guarded game routes expose only the last entry to NavDisplay. Each binding owns its save/leave confirmation. One NavDisplay, not two navigation engines. Back source/platform wiring and detailed UI tests remain under review.
- App DI uses process-owned multiplayer scope/owner and game composition-root registrations; desktop in-memory secure storage is not selected on mobile. App language/theme state wraps content without an explicit language-keyed session recreation.
- Lifecycle policy distinguishes inactive privacy covering from real background transport suspension; Android config-replacement tracker suppresses invented background/foreground cycles. Platform callback delivery and actual native covering still need their own review/runtime evidence.

There is still an unexecuted iOS error-injection/lock-transition test gap, NOT a confirmed crash. macOS API observation is not iOS application/device proof.

## Authoritative research (accessed 2026-09-05)

- Apple `https://developer.apple.com/documentation/foundation/filehandle/readdata(oflength:)`, JSON evidence `evidence/apple-filehandle-read-doc.json`: legacy read API raises fileHandleOperationException on failed type determination/read. iPhoneSimulator26.5 SDK header corroborates replacement; current documentation's future deprecation must not be described as already deprecated on iOS26.
- Kotlin `https://kotlinlang.org/docs/native-definition-file.html#handle-objective-c-exceptions`, saved HTML: Objective-C exceptions terminate by default unless wrapping explicitly enabled. `https://raw.githubusercontent.com/JetBrains/kotlin/v2.4.10/kotlin-native/platformLibs/src/platform/ios/Foundation.def` saved exact tagged source has no wrapping setting.
- Kotlin ObjC interop documentation was also consulted, but its Swift/NSError discussion alone is not proof of NSException semantics; it is a lead, not the decisive source.
