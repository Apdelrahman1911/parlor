## ✅ 2026-07-28 production remediation

The current production implementation closes the previously deferred
`mafia-ui-003` and equivalent Whodunit host-flow gap. A disconnected required
seat now blocks gameplay behind a localized host recovery surface. The host can
wait, leave, or confirm `ContinueWithoutPlayer`; that transition is bridge-owned
and cancels the pending grace job before publishing the authoritative state.
Focused lifecycle tests cover the manual decision, duplicate attempt, and
timer-cancellation paths for both games. Physical-device UX remains a release
gate in `docs/RELEASE_GATES.md`.

### Top blockers (fix these first)

1. **Privacy leaks that expose the killer/mafia roles** — the single most important class for this app. The role-assignment seed is broadcast to all peers (`NN-01`), HostOnly secrets are persisted to disk in plaintext (`storage-01`), and per-player private slices are routed by an unauthenticated peer id so a spoofed id receives another player's role (`p2p-007`).
2. **Action-authority bypass** — the host trusts a peer's self-attested `sender`, so a peer can forge another player's vote/night action (`wu-ui-01`).
3. **Multi-device host can't play** — the host renders against the PUBLIC projection and never sees their own role / night actions (`mafia-ui-001`).
4. **App cannot be released** — `parlor.p2p.enabled=true` is committed as default (breaks every clean build/CI without P2pKit in mavenLocal) (`bc-01`); there is no Android release build type / signing / R8 / shrink (`bc-02`); placeholder app icons (`bc-06`).

## ✅ 2026-06-13 audit pass — multi-device deadlocks + reconnect (review on Fable-5, fixes verified green)

A second exhaustive pass (four parallel layer reviewers — core app, Whodunit, Mafia,
P2pKit integration — each cross-checked against this catalogue, then every load-bearing
claim re-verified against the real code before any change). It surfaced a class of
**multi-device deadlocks the May pass missed**, plus confirmed several catalogued-but-open
items. All fixes below were implemented and **verified green**:
`:game-modes:whodunit:desktopTest` (142, +3 new) · `:game-modes:mafia:desktopTest`
(128, +3 new) · `:shared:transport-p2p:desktopTest` (22, +3 new) · `:shared:session:desktopTest`
(16) — **0 failures**; `:composeApp:compileDebugKotlinAndroid` + iOS-target compiles green.
The multi-device runtime fixes are validated on hardware by `docs/PARLOR_P2P_SMOKE_TEST.md`.

**🔴 Mafia multi-device was unplayable — now progresses end-to-end:**
- **Gated-advance gap** (the compounding NOTE under `mafia-ui-001`, never fixed) — the
  multi-device router only ever submitted `OpenVote` + `ResolveNight`; nothing drove
  `AdvanceFromRoleAssignment` / `OpenDiscussion` / `CloseVote` / `AdvanceFromVoteAnnouncement`,
  so the game **deadlocked at role-assignment → night** (and every later gate).
  `PartyAwareSession` only auto-fills acks in *local* play. Fix: a host-only
  `HostPhaseProgressionDriver` (`MafiaMultiDevicePhaseRouter.kt`) backed by a **pure,
  unit-tested `nextHostAdvance(state)`** that submits each advance once its readiness gate
  holds — mirrors the pass-and-play auto-fires. New `MafiaMultiDeviceProgressionTest` drives
  a full game to a winner using *only* `nextHostAdvance` for the advances.
- **Dead-host night-resolution deadlock** (NEW) — the only `ResolveNight` control lived in
  the alive-host branch, so a killed host could never resolve subsequent nights. The driver
  now resolves the night off the *living* players' submissions, independent of host aliveness.

**🔴 Whodunit reducer deadlocks (NEW — both stranded the room on a blank screen):**
- **TiedRevote → innocent elimination** — an Elimination revote that eliminated an innocent
  left `phase = TiedRevote` with a `Resolved` voteState; `acknowledgeRevealCard` is
  Round-gated, so it could never advance. Fix: normalise the phase back to the current
  `Round` in `resolveVote`'s innocent-continue branch. Regression test added.
- **All-abstain `NoResolution`** — every voter abstaining produced a `NoResolution` voteState
  that no screen consumed. Fix: `closeVote` now resolves it like an unresolved tie (Classic →
  killer wins; Elimination → next round). Two regression tests added.

**🟠 Multi-device state-loss & recovery:**
- `CC-01` (NEW root-caused) — both host flows keyed `sessionConfig`/`rawSession` on the
  **live** `players` list, so a peer drop/return mid-game rebuilt the controller and wiped
  roles/phase/votes for everyone. Fix: freeze the roster at start (`remember { players }`);
  membership churn flows through `MarkPlayerDisconnected/Reconnected`.
- `p2p-003` (peer recovery) — `ReconnectPolicy` was left at the SDK default `Disabled`, so a
  peer's outgoing session went to a **terminal** HostLost on any blip (the "Reconnecting…"
  overlay never cleared). Fix: all three factories now configure
  `ReconnectPolicy.Enabled(10, 3s)`; the transport's existing Reconnecting/HostRestored
  handling becomes live. **(Validate on hardware — smoke D1.)**
- Manual-rejoin gap (NEW) — a peer that left and rejoined mid-game was stranded on "waiting
  for host to start" because reconnect resent snapshots but not `SessionStarting`. Both host
  bridges now retain and re-send `SessionStarting` to a reconnecting peer.

**🟠 Mafia reducer:**
- `mafia-002` — dropped-but-alive players were still counted in win-check and still cast
  night actions. Fix: win parity and night submissions now exclude `droppedPlayers`
  (`isActiveAlive`).

**🟠 P2pKit transport lifecycle:**
- `p2p-016` — `leave()` (host + peer) is now idempotent (`left` guard) and wraps the terminal
  `kit.stop()` in `runCatching`, so the Leave-tap + `onDispose` double-call can't throw.
- `p2p-005` — `host()` now stops the kit if `start()/startAdvertising()` throws (was leaking
  a started instance). `p2p-014` — broadcast to zero Connected peers now returns
  `NetError.NotConnected` instead of a silent success. Three transport regression tests added.

**🟡 Whodunit reducer hardening (catalogued-open, now fixed):**
- `wd-06` `assignRoles` now guards a degenerate roster instead of `require()`/`first()`
  throwing in the pure reducer · `wd-07` `castVote` no longer double-increments
  `currentVoterIndex` on a recast · `wd-12` `continueWithoutPlayer` clears `disconnectedPlayers`
  and `markPlayerReconnected` won't un-drop a spectator · `wd-16` Elimination second-tie now
  caps at the final two (was an unbounded round loop) · dropped players are no longer votable
  targets (`castVote` target guard).

**Documented but NOT applied (need new UI / hardware / infra — tracked):**
- `mafia-ui-003` / Whodunit equivalent — **no host UI to `ContinueWithoutPlayer`**, so a peer
  that disconnects and never returns still blocks the readiness-gated advances. The reducer
  path exists; it needs a host "continue without {player}" control (a UI affordance best
  validated on devices). Highest-value remaining multi-device item.
- The long tail of catalogued Low items (toast thread-safety, settings persistence, content
  cache poisoning, storage path-sanitisation, etc.) remains as previously documented.

### Multiplayer security/privacy pass (validated against P2pKit + in-memory tests)

After republishing P2pKit `0.6.0` (with `maven-publish` wiring added) to mavenLocal and rebuilding Parlor with `parlor.p2p.enabled=true`, the following were **fixed and verified green** (`315 desktopTest, 0 failures`, including 2 new security regression tests, with `:shared:transport-p2p` + `composeApp` p2pEnabled compiling against the real P2pKit):

- `p2p-002` *(high)* — `HostP2pRoom`/`PeerP2pRoom` collectors now `runCatching` the JSON decode and skip+log a bad frame instead of letting a `SerializationException` cancel the collector and permanently sever the session's inbound stream.
- `p2p-001` *(high)* — all `HostP2pRoom` membership-map access is now serialized by a `Mutex` (chosen over a confined dispatcher so coroutines stay on their dispatcher and tests remain deterministic); `send()` snapshots the session list under the lock before iterating.
- `NN-01` *(critical, privacy)* — the role-assignment seed is **no longer broadcast**. `HostMessage.SessionStarting.seed` → `sessionNonce`, a public room-code-derived value used only for peer SessionId naming; the role seed stays host-only. Regression test `session_starting_does_not_leak_role_seed` asserts the wire nonce ≠ the role seed.
- `wu-ui-01` / `NN-03` *(critical, authority)* — the actor identity is now the **transport-authenticated** sender, not the self-attested `ActionSubmit.sender`: `P2pKitRoomTransport` overwrites it with the session's bound peer id, and `InMemoryPeerRoom` stamps its own `selfPlayerId`. Regression test `peer_cannot_forge_sender_to_impersonate_another_player` proves a forged `sender` is rejected.

### Documented but intentionally not applied here
Specified with concrete fixes in their entries below; not applied because each needs work that cannot be safely implemented or verified in this environment:

- **`p2p-006` / `p2p-007` (peer authentication & full seat binding)** — the remaining #1 item. A crypto-less, application-layer admission handshake would be **security theater**: the room code already travels in cleartext over Bonjour, and `commonMain` has no HMAC primitive. The complete fix is a **P2pKit `SecurityMode`** (transport encryption + authenticated peer identity, which would let Parlor *trust* `session.peer.id`) **or** a lobby redesign with **host-assigned seat ids** decoupled from the spoofable peer id. The `wu-ui-01` fix above already binds *actions* to the authenticated connection; full private-state-routing protection against a peer that spoofs the victim's peer id at connect requires one of those two paths — and a **real two-device run** to validate.
- **At-rest encryption** — `storage-01` / `storage-02` (HostOnly secrets persisted plaintext; `SecureStorage` has no platform backing) need Android Keystore / iOS Keychain / desktop key-derivation `actual`s.
- **Persistence & resume** — `storage-03` / `CC-02` (settings reset every launch), `storage-04` (snapshot `engineVersion` never checked), `CC-03` (resume always routes to Whodunit) need platform persistence actuals / a game-aware resume.
- **App-store release** — `bc-02` (release build type / signing / R8 / shrink) needs an upload keystore; `bc-06` / icons / manifest split need icon assets.
- **`mafia-ui-003`** (no Continue-without-player affordance → disconnect deadlock) needs a new host UI control.
- The long tail of low-severity docs / dead-code / test-quality items — each has a concrete proposed fix in its entry below.

## 🔴 Critical findings

#### 🔴 `bc-02` — No Android release build type, signing config, minify/R8, or shrinkResources — app cannot be released
- **File:** `composeApp/build.gradle.kts:114-138`
- **Category:** build · **Fix validation:** ✅ no hardware needed
- **Problem:** Confirmed by reading the android {} block (namespace, compileSdk=36, defaultConfig with applicationId/minSdk26/targetSdk35/versionCode1/versionName1.0.0, compileOptions, buildFeatures.compose, packaging excludes) and by a repo-wide grep: ZERO matches for buildTypes / isMinifyEnabled / shrinkResources / signingConfig / proguardFiles / isDebuggable anywhere in any .kts/.gradle. `find` for *.pro returns nothing. AndroidAppConventionPlugin.kt also has no release/signing config and is not applied (see bc-03). assembleRelease/bundleRelease therefore produce a debug-signed (or unsigned), non-minified, non-shrunk artifact.
- **Impact:** Cannot publish to Google Play: a debug-keystore-signed APK/AAB is rejected and an unsigned release is impossible. No code shrinking/obfuscation. Hard app-store release blocker.
- **Fix:** Add signingConfigs sourcing the upload keystore from env/gradle.properties (never committed) and a buildTypes { release { isMinifyEnabled = true; isShrinkResources = true; proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro"); signingConfig = signingConfigs.getByName("release") } }. Pair with the keep rules from bc-04.

#### 🔴 `mafia-ui-001` — Multi-device host renders against the PUBLIC projection, so the host player can never see their role or take night actions
- **File:** `game-modes/mafia/src/commonMain/kotlin/com/parlor/games/mafia/ui/flow/multidevice/MafiaMultiDeviceHostFlow.kt:118-135`
- **Category:** correctness · **Fix validation:** ✅ no hardware needed
- **Problem:** Verified end-to-end. MafiaMultiDeviceHostFlow.kt:118-119 does `val publicProjection by session.publicState.collectAsState(); val state = publicProjection.state`. `session` is a PartyAwareSession (line 102-105) whose `publicState` delegates to PassAndPlaySessionController.publicState (PartyAwareSession.kt:43), which maps through `policy.toPublic(it)` (PassAndPlaySessionController.kt:66-68). MafiaProjectionPolicy.toPublic (MafiaProjectionPolicy.kt:45-51) sets `privatePerPlayer = emptyMap()` and `hostOnly = redactedHostOnly`. The host IS a seated player: MafiaHostLobbyFlow.kt:116-124 builds `listOf(hostPlayer) + peers` with hostPlayer at seat 0 and id = hostPlayerId = room.selfPlayerId. The router reads `state.privatePerPlayer[selfPlayerId]` (MafiaMultiDevicePhaseRouter.kt:118) which is therefore always null on the host -> RoleAssignmentSegment shows waiting_role_pending forever (priv==null, line 235), NightSegment shows waiting_night_pending forever (line 275). Peers do NOT have this bug: MafiaMultiDevicePeerFlow renders the ShadowSessionController's publicState (ShadowSessionController.kt:42 returns _public unchanged), and MafiaPeerRoomBridge.handlePublic/handlePrivate merge the self slice into privatePerPlayer[self] (lines 140-143, 154-159). So the host is uniquely broken.
- **Impact:** Multi-device Mafia deadlocks at role assignment: the host (a seated player) can never view/ack their role; even if it advanced, the host could never submit night actions. The core multi-device flow is unplayable. NOTE (compounding): the multi-device router/flows ALSO never submit AdvanceFromRoleAssignment, OpenDiscussion, or AdvanceFromVoteAnnouncement anywhere (grep shows these are only submitted in MafiaPassAndPlayPhaseRouter) — so the gated host advances have no UI trigger in multi-device regardless. Fixing 001 is necessary but not sufficient to make multi-device playable.
- **Fix:** Render the host router off `session.hostState!!.value.state` (full state) exactly as the pass-and-play flow does (MafiaGameFlow.kt:166: `val hostProjection by session.hostState!!.collectAsState()`), so privatePerPlayer[selfPlayerId] and hostOnly are populated. Alternatively (per Whodunit's PhaseRouter, WhodunitPhaseRouter.kt:481/546/659) have the router obtain the self slice via `session.privateStateFor(selfPlayerId)` and merge it. Option (a) is simplest. Separately wire UI affordances (or auto-fire) for AdvanceFromRoleAssignment / OpenDiscussion / AdvanceFromVoteAnnouncement in the multi-device flow.

#### 🔴 `wu-ui-01` — Host trusts peer self-attested `sender` in ActionSubmit — ActionAuthority gate is bypassable (vote/action forgery)
- **File:** `game-modes/whodunit/src/commonMain/kotlin/com/parlor/games/whodunit/ui/flow/multiplayer/WhodunitHostRoomBridge.kt:155-171`
- **Category:** security · **Fix validation:** ✅ no hardware needed
- **Problem:** Verified against the real code. startActionInbox() (lines 158-169) decodes PeerMessage.ActionSubmit and at line 165 calls WhodunitActionAuthority.isAllowed(action, msg.sender, hostId, droppedPlayers) using the body-supplied msg.sender. Protocol.kt:58-65 documents sender as 'the peer's self-attested PlayerId'. Neither transport reconciles it against the authenticated session: P2pKitRoomTransport.HostP2pRoom knows the real peer id as PlayerId(session.peer.id.value) (line 332) but its per-session collector (351-369) just tryEmit(decoded) with sender intact — no decoded.sender == session.peer.id check. InMemoryRoomBus.fromPeer (57-59) forwards verbatim. The SelfActor rule (WhodunitActionAuthority.kt:104-107) is senderId == scope.actor, so a peer setting sender to another player's id passes for CastVote/RefuseToVote/AbstainVote/CompleteCharacterReveal/SubmitStructuredAction. Same bug in MafiaHostRoomBridge.kt:166.
- **Impact:** Any peer on the multi-device (P2P) topology can impersonate any other player for all SelfActor actions — forging votes (vote-stuffing against the suspected killer), reveal acks, structured actions. Defeats the ActionAuthority guarantee. Scope: only the opt-in multi-device path (parlor.p2p.enabled); pass-and-play/solo MVP is unaffected. Multi-device release blocker.
- **Fix:** Derive actor identity from the authenticated transport session, not the message body. The transport has PlayerId(session.peer.id.value); surface it to the bridge (wrap inbound messages with an authenticated peer id, or reject/overwrite any ActionSubmit whose sender != delivering session's peer id), then pass the authenticated id to isAllowed. Apply the same fix to MafiaHostRoomBridge and update Protocol.kt's self-attestation contract.

#### 🔴 `bc-01` — parlor.p2p.enabled=true committed as default breaks every clean build / CI / release without P2pKit in mavenLocal

#### 🔴 `NN-01` — SessionStarting broadcasts the deterministic role-assignment seed to all peers, leaking the killer (HostOnlyState)
- **File:** `shared/networking/src/commonMain/kotlin/com/parlor/networking/protocol/Protocol.kt:45-51`
- **Category:** privacy · **Fix validation:** ✅ no hardware needed
- **Problem:** VERIFIED end to end. HostMessage.SessionStarting carries seed: Long (Protocol.kt:50). WhodunitHostRoomBridge.announceStart sends it with SendTarget.Broadcast (WhodunitHostRoomBridge.kt:74-83). The SAME seed is fed to WhodunitAction.AssignRoles(seed) (WhodunitGameFlow.kt:673 announceStart(seed=seed); :684 session.submit(WhodunitAction.AssignRoles(seed)); both read the identical `seed` local set at :651 RandomSource.seeded(seed)). assignRoles derives the killer purely deterministically from it: WhodunitReducer.kt:97 RandomSource.seeded(seed), :102 random.shuffled(characters) (seat->character), :107 random.pick(players) (killer), :108 killerCharacterId. RandomSource.seeded wraps kotlin.random.Random(seed) (RandomSource.kt:24-25) — a pure-Kotlin cross-platform deterministic PRNG, identical sequence on every target. Case content is a public CMP resource bundled in every client. The leak BYPASSES the projection entirely: WhodunitProjectionPolicy.toPublic correctly redacts hostOnly.randomSeed (WhodunitProjectionPolicy.kt:29,45) in the state snapshot — but the identical secret is shipped in cleartext via the separate SessionStarting message, rendering that redaction moot. Any peer holding the broadcast seed recomputes the exact role map and the murderer offline. This is the canonical CRITICAL HostOnlyState leak the three-bucket model exists to prevent.
- **Impact:** Complete compromise of the core game secret in multi-device Whodunit: a curious/malicious peer recovers the killer's identity at game start from public inputs, ruining the game and violating the load-bearing privacy invariant (ARCHITECTURE.md §7). The same construction applies to Mafia role assignment (MafiaHostRoomBridge.announceStart also takes seed: Long — MafiaHostRoomBridge.kt:84).
- **Fix:** Do not transmit the role-assignment seed to peers. Remove `seed` from HostMessage.SessionStarting (Protocol.kt:50) and from both host bridges' announceStart. NOTE the fix is slightly larger than 'delete the field': peers currently CONSUME start.seed — WhodunitMultiplayerPeerFlow builds createInitialState(SessionConfig(randomSeed = seed)) and SessionId("mp-peer-${seed.toString(16)}") (WhodunitGameFlow.kt:761-771), and PeerSessionFlow.kt:113,219 thread it through. But peers never reduce: ShadowSessionController.submit only forwards to the host and hostState is null; real state arrives via updatePublic/updatePrivate snapshots. So the seed is not actually needed for peer correctness — the peer's initial Setup-phase state (empty privatePerPlayer/hostOnly) is overwritten by the host's first snapshot. Replace the peer's use of `seed` with a host-supplied non-secret display nonce (unrelated to RandomSource.seeded), or derive the peer SessionId from the room code. Keep the AssignRoles seed inside HostOnlyState only. Add a unit test asserting SessionStarting carries no field equal to the reducer seed, and a guard test that no broadcast HostMessage exposes a value reproducing the killer.

#### 🔴 `storage-01` — HostOnly secrets (killer identity / killer seed) are persisted to disk in plaintext
- **File:** `shared/storage/src/commonMain/kotlin/com/parlor/storage/snapshot/FileBackedSnapshotStore.kt:29-37`

#### 🟡 `p2p-009` — Inbound message + peerEvents flows use tryEmit on a bounded buffer — messages/events silently dropped under backpressure
