# Shell and design-system usability overhaul

Tracking: [#259](https://github.com/Apdelrahman1911/parlor/issues/259).

## Scope and evidence boundaries

This work changes implemented Compose screens, not mockups: catalog, device-mode
selection, join onboarding, settings, shared room invitation/roster, and navigation
headers. The shared components also apply to game screens. Individual game boards
are separate workstreams. This report does **not** certify the entire application
or claim physical-device/VoiceOver/TalkBack acceptance.

## Findings and implemented design

| Finding | Evidence / impact | Resolution |
| --- | --- | --- |
| Multiplayer-only games advertised local play | `HomeScreen` chose “Local + same Wi-Fi” using only LAN capability; the three multiplayer-only bindings cannot enter a local session. | Local and nearby capabilities are evaluated independently; accurate metadata and capability-based filters. Pure capability regression tests include future single-mode bindings. |
| Catalog discovery required excessive scrolling | Each game used display-sized title, subtitle, tagline, large artwork and metadata, after a long narrative hero. | Compact game identity, concise tagline, player count/mode, clear opening action; optional All / One device / Nearby filters. Saved-session recovery remains independent of filters. |
| Phone mode choices squeeze large Arabic text | Host/join used unconditional half-width cards. | `AdaptiveOptions` stacks at narrow width **or** enlarged font scale, uses equal columns only when readable, and preserves logical RTL order. Multiplayer choices now precede local alternatives. |
| Back affordance reduced title width on every line | Shared header placed the complete title/subtitle column beside the back button. | Separate navigation row; title and explanation receive the full content width. |
| Joining lacked contextual progression | Single network paragraph did not distinguish finding a room from admission. | Three persistent inline steps explain shared Wi-Fi, code, and host approval without a blocking wizard or false immediate-entry promise. |
| Lobby roster lacked explicit role/connection labels | Bare names did not distinguish host from admitted connected players. | Grouped roster with textual host/connected status and polite count announcements; invitation explains approval and start. No player secrets or credentials exposed. |
| Room code used an oversized display font | Six-character code at 200% text could exceed compact card width. | Scalable monospaced room code with explicit LTR direction; no font-scale suppression. |
| Shared context ribbon fragmented privacy instructions | Actual rendered Mafia screenshot at 320dp / 200% broke “PRIVATE SCREEN” into “PRIVAT / E SCREE / N”; Arabic authority copy also broke midword. | Reuse adaptive stacked layout with full-width label and explanation, preserve private/inverted color tokens and grouped semantics; explicit EN/RTL layout regression. |
| Settings selections were unclear before choosing | Unselected choices had no radio affordance. | Persistent native radio indicators, one row-level accessible action, and short group explanations. |

## Shared interaction rules

- Reuse existing audited light/dark contrast tokens and game accents, not new
  unaudited colors. Use text as well as color for state.
- Back/navigation precedes the title; the next useful action remains explicit.
- Controls retain minimum targets (52dp buttons; 48dp filters), intrinsic text
  heights, scrolling, and logical RTL/LTR layout. Never ellipsize essential copy.
- No new timers, continuously animated ornament, per-frame polling, background
  work, or bitmap assets. Existing reduced-motion behavior remains intact.
- `AdaptiveOptions` is for peer choices, not hidden/private player information.
  `QuickStartSteps` provides small inline tutorials at the point of use.

## Research consulted (2026-10-25)

- [Android Compose accessibility defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults): minimum 48dp touch targets, semantic interaction roles.
- [Android adaptive display sizes](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-display-sizes): adapt layout to available width rather than assuming a phone model.
- [Apple HIG accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility): support at least 200% text, sufficient contrast, status beyond color, comfortably sized controls, simple gestures, reduced automatic motion. The official documentation JSON was retrieved and inspected, not inferred from a search snippet.

reading order, full-width titles, and back callbacks. Initial app compilation
found a malformed settings modifier chain introduced by this patch; it was
corrected and the next production app compile passed. Focused app rendering
subsequently passed on the UX worktree as documented below; this does not certify
the separate combined integration checkout.

### Focused app rendering result

The UX worktree passed **31 tests, zero failures/errors/skips** on 2026-10-25:

```sh
xvfb-run -a ./gradlew :composeApp:desktopTest \
  --tests '*HomeCatalog*' --tests '*PlayModePickerRenderingTest*' \
  --tests '*SettingsScreenRenderingTest*' --tests '*RoomGameLobbyRenderingTest*' \
  --tests '*ProductionUiAccessibilityContractTest*' \
  --tests '*LocalizationResourceContractTest*' \
  --dependency-verification=strict --max-workers=2 \
  -Pkotlin.compiler.execution.strategy=in-process \
  -Dorg.gradle.jvmargs='-Xmx3g -XX:MaxMetaspaceSize=1g -Dfile.encoding=UTF-8'
```

The first run exposed a test assumption: at 200% Arabic text, the second lazy
catalog item is not composed until scrolled into view. The regression now scrolls
the lazy container to that content before asserting it; no assertion was removed.
Actual screenshot inspection also found Material-default purple filter selection;
filters now explicitly use the audited Parlor theme palette.

All 16 generated `home-{en,ar}-{light,dark}-{1.0,2.0}.png` and
`setup-{en,ar}-{light,dark}-{1.0,2.0}.png` frames under
`composeApp/build/reports/ux/` were visually inspected. Text remains readable,
RTL order is correct, and 200% setup options stack rather than squeeze labels.
The screenshot fixture now uses the production multiplayer contract's player
bounds (Whodunit's shipped six-player case), not theoretical definition bounds.
This is Desktop Compose evidence, not Android/iOS device or screen-reader evidence.

Screenshot inspection prompted one further adaptive fix: at 150% text and above,
Home omits only its decorative eyebrow and marketing subtitle, retaining the
heading and the user's full text scale. Wrapped filters now have a vertical gap.
The focused 31-test suite passed again after this change (zero failures/errors/
skips); all eight updated Home images were inspected. In both languages/themes
at 200%, the first game's clickable card is visible without scrolling, enforced
by a new rendering assertion. This is partial card visibility, not a claim that
its full description and footer fit in one viewport. Setup is unchanged.

Full game journeys, saved-session-heavy catalog layouts, assistive technologies,
and physical-device acceptance remain outside this focused shell result.
